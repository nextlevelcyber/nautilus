# hftbacktest 与 NautilusTrader 对比：加密团队回测基础设施选型（v2）

本版是第一版对比的纯文档版本，去掉了代码标识、文件路径和行号引用，只保留结论和理由，便于非技术读者阅读。

- **hftbacktest** 的结论来自对其仓库代码、文档和教程 notebook 的核实（团队 fork 的浅克隆）。
- **NautilusTrader** 的结论以同目录下的 Nautilus 评估文档为准，文中写作"Nautilus 评估"。
- 需要逐条查证出处时，请看同目录下的第一版对比文档。
- 标"（推断）"的结论不是文档或源码的直接陈述，而是推理得出的。评级沿用 Nautilus 评估：强 / 较强 / 部分 / 弱。

## 1. 结论摘要

**两者定位不同，不是同一层次的替代品。** hftbacktest 是一个单机运行、逐笔级别、对延迟和排队高度敏感的微观结构回测器，
附带一个最小化的实盘机器人；NautilusTrader 是一个支持多交易所、带账户和组合管理、回测与实盘共用一套代码的交易引擎。
团队的五类工作分别落在两者各自的强项上，没有一方能单独覆盖。

**逐场景胜出方**：

- **做市：hftbacktest 胜（强 vs 较强）。** 决定性差异是延迟建模。hftbacktest 让同一条行情分别在"交易所侧"按交易所时间、
  在"本地侧"按本地接收时间生效，从而模拟出行情延迟；下单延迟也拆成"发往交易所"和"回报传回"两段，还能按历史实测延迟插值。
  Nautilus 只延迟下单方向。排队模型方面，hftbacktest 提供 6 种 L2 模型（1 种保守模型加 5 种概率模型）和 1 种 L3 先进先出模型，
  可以调参去贴合实盘。
- **跨所套利：Nautilus 胜（较强 vs 部分）。** hftbacktest 能把多个资产、多个交易所放进同一个回测，
  但每个资产的账户相互独立、余额从 0 开始，没有保证金、资金费结算和跨所共享余额，官方示例也全是"单资产加多进程"。
  Nautilus 有按交易所划分的账户、资金费结算和组合视图。
- **延迟评估：hftbacktest 明显胜（强 vs 部分）。** 行情延迟、下单发出延迟、回报延迟三者都能建模，都能换成实测数据，都能整体平移做扫描，
  还有一个工具可以"用行情延迟合成下单延迟"。
- **因子研究：两者都弱。** 都没有向量化或横截面的因子计算接口。hftbacktest 的 IC 计算和"时间 × 品种"矩阵研究，
  只出现在一份标注为草稿的教程 notebook 里，不是库本身的功能。
- **行情数据评估：hftbacktest 略胜（部分 vs 弱）。** 它自带数据采集器，会记录本地接收时间，并在序列号断档时重新拉取快照，
  还有时间戳校正和事件顺序校验工具。但两者都不出数据质量报告，交易所间一致性对比、数据商对比都要自建。

**总体建议（推断）**：现实答案是**组合使用，以 Nautilus 为主平台**。

- Nautilus 负责多交易所策略、账户与组合、跨所套利、实盘部署，以及团队共享的数据目录。
- hftbacktest 作为"微观结构实验室"，专门用于做市报价与排队研究、延迟敏感性评估、行情时序质量评估。
- 不建议把 hftbacktest 当作唯一平台：它的实盘只在 Binance 合约的测试网上验证过；账务用浮点数、没有组合层；核心代码由一位作者维护（见 3.10 节）。
- 组合的代价是两套数据格式和两套策略代码，策略不能直接搬过去。
  所以组合方案的关键投入是**统一的原始数据层**：同时保留交易所时间和本地接收时间，再分别生成两边需要的回测格式（见第 5 节）。

## 3. 关键维度对比

### 3.1 订单簿与排队建模

- **订单簿重建**：两者都支持 L2（按价位聚合）和 L3（逐笔订单）。hftbacktest 有四种订单簿实现，其中一种在丢包时能自然刷新最优价，
  另一种在丢包时可能出现买卖价交叉。
- **L2 排队模型**：hftbacktest 有一个保守模型和一组概率模型，概率模型提供 5 种概率函数，有一个可调参数用来贴合实盘。
  Nautilus 只有一种确定性规则：挂单被受理时记下前面排着多少量，之后随对手方成交逐步扣减。
- **L3**：hftbacktest 的 L3 模型明确假设所有交易所都按"价格优先、时间优先"撮合；Python 侧不允许把 L3 和部分成交模型一起用。
  Nautilus 的 L3 按逐笔订单精确推进队列。
- **自身冲击**：两者都不模拟。hftbacktest 文档明确写明"你的订单不能改变模拟市场"；L3 下回测订单只进入排队模型，不写入订单簿（推断）。
- **小结**：做市排队研究上 hftbacktest 更灵活，模型多且可以校准；Nautilus 有一个可选的"流动性消耗"开关，
  在"同一档被多张模拟单重复成交"的问题上更保守。

### 3.2 延迟建模（行情与下单，发出与回报）

| 延迟分量                   | Nautilus                           | hftbacktest                                                      |
| -------------------------- | ---------------------------------- | ---------------------------------------------------------------- |
| 行情延迟（交易所到本地）   | 不模拟，数据按接收时间回放         | 模拟：同一事件在交易所侧按交易所时间、在本地侧按接收时间生效     |
| 下单发出（本地到撮合）     | 支持，下单、改单、撤单各有一个回调 | 支持                                                             |
| 回报（撮合到本地，含成交） | 不模拟                             | 支持，成交回报同样受这段延迟影响                                 |
| 实测延迟回放               | 自定义模型按订单查表               | 按实测的请求、撮合、回报三个时间线性插值                         |
| 交易所拒单                 | 未找到                             | 实测数据里撮合时间无效即视为拒单                                 |
| 按下单、改单、撤单区分     | 支持                               | 不支持，仍在路线图上；用 Rust 写自定义模型理论上可以区分（推断） |
| 采集点平移                 | 未找到                             | 行情延迟和下单延迟都可以整体平移                                 |

hftbacktest 的两个限制：

- 假设请求和回报保持先后顺序，不模拟 REST 请求乱序到达。
- Python 侧只能在"固定延迟"和"实测延迟插值"两种模型中选。自定义模型只能用 Rust 写，或者在 Python 里先生成延迟数据，再交给插值模型。

### 3.3 多交易所

- **Nautilus**：一个引擎内多交易所、多账户；延迟、成交、手续费模型都能按交易所配置；有资金费结算和组合敞口。
- **hftbacktest**：
  - 一个回测能包含多个资产和多个交易所，每个资产可以配不同的排队模型和资产类型。
  - 所有资产的交易所侧数据、本地侧数据和订单事件放在同一个调度器里，每一步取时间最早的事件，所以多个交易所在同一条时间轴上同步。
  - 但所有资产必须用同一种订单簿实现。
  - 每个资产的账户独立，余额、持仓、费用都从 0 开始。没有共享资金池、保证金、强平或资金费结算；
    资金费率只能在 Binance 转换工具里作为自定义事件写入数据。
  - Python 示例全是单资产回测，多资产是用多进程并行跑独立回测，再在 notebook 里手工加总权益。跨市场做市示例还在路线图上。

### 3.4 数据格式与接入（交易所数据、Databento、Pyth）

| 来源               | Nautilus                                                               | hftbacktest                                                                             |
| ------------------ | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 存储格式           | Parquet 数据目录，可放在 S3、GCS、Azure                                | 8 个字段的 numpy 数组文件，每条记录 64 字节，可以从 S3 读取；Parquet 还在路线图上       |
| 自有交易所原始数据 | 通用 CSV 加载工具、格式转换工具、Binance 深度 CSV 加载工具             | 需要转成它的 8 字段格式并标记交易所侧、本地侧事件；可以复用它的时间戳校正和顺序校验工具 |
| Tardis             | CSV 加载和回放服务                                                     | 支持成交、L2 增量和最优挂单，另有多数据流融合转换                                       |
| Databento          | 覆盖逐笔订单、最优报价、十档深度、成交、K 线等；接收时间被当作事件时间 | 只支持逐笔订单；交易所时间和接收时间都保留                                              |
| Pyth               | 没有接入，需要做成自定义数据                                           | 未找到任何支持；只能按教程演示的"按本地时间查表"方式接入                                |

### 3.5 实盘路径

- **Nautilus**：17 个官方接入，加密交易所覆盖 Binance、Bybit、Coinbase、Deribit、dYdX、Hyperliquid、Kraken、OKX 等；
  有执行对账；回测和实盘用同一套策略代码。
- **hftbacktest**：
  - Rust 侧回测和实盘共用同一份策略代码。
  - 实盘连接器只覆盖 Binance 合约（只在测试网验证过）和 Bybit（开发中），代码里另有 Binance 现货。
  - 机器人和连接器通过共享内存通信，必须在同一台机器上。
  - 连接器启动时会撤销全部挂单来获得干净状态，没有找到持仓和挂单的对账逻辑。
  - Python 实盘绑定存在，但官方发布的 Python 包默认不包含实盘功能；README 标注实盘"仅支持 Rust"，Python 实盘还在路线图上。

### 3.6 分析、报表与界面

- **Nautilus**：34 个统计量、各类报表表格、自包含的交互式 HTML 报告；网页界面明确不在项目范围内。
- **hftbacktest**：
  - Python 统计模块有 17 个指标，包括夏普比率、索提诺比率、最大回撤、收益回撤比、最大杠杆。
  - 年化默认按 252 天，文档提示加密市场可以改成 365。
  - 记录器只按固定时间间隔采样每个资产的价格、持仓、余额、费用和成交次数，不是逐笔成交日志。
  - 画图用 matplotlib 或 holoviews。
  - 没有界面，也没有组合层面的报表；中心化的编排工具还在路线图上。
- **结论**：两者都要自建网页后台；Nautilus 的报表和结果更完整。

### 3.7 Python 与 Rust 的易用性

- **hftbacktest**：
  - Python 策略必须写成 Numba 即时编译的函数，导入库和第一次编译策略都要花时间。
  - Numba 只支持 Python 的一个子集，团队现有的 pandas 或面向对象代码不能直接放进策略循环（推断）。
  - 排队模型、交易所模型、延迟模型的自定义只能用 Rust 写；Python 只能从固定的选项中选择。
  - Python 侧的默认配置是：一种概率排队模型、不部分成交、零延迟、零手续费。零延迟这个默认值很容易让结果过于乐观（推断）。
- **Nautilus**：Python 策略是普通的 Python 类，回调同步执行；Python 里就能自定义延迟模型和成交模型。
- **小结**：一般研究员上手 Nautilus 更容易；需要改撮合或排队假设时，两边都要写扩展，但 Nautilus 在 Python 里能扩展的地方更多。

### 3.8 性能

- **hftbacktest**：仓库里没有正式基准，只有 notebook 里的计时输出，硬件也没说明：
  - BTCUSDT 一个月（2023 年 5 月）的全量 L2 回放，加一个订单簿失衡做市策略，墙钟时间约 33 分钟。
  - BTCUSDT 一天的完整回测用时 1 分 49 秒；"加速回测"（不模拟排队和回报延迟、预先计算成交条件）只要 416 毫秒，约快 260 倍。
    但加速回测是 notebook 里手写的代码，不是库的功能。
  - 调度器每一步都要线性扫描一遍所有资产的事件时间，资产很多时可能成为瓶颈（推断）。
- **Nautilus**：官方基准只覆盖单交易所的 K 线加报价，没有多交易所 L2 的吞吐数据；大量成交累积到同一持仓时 v2 比 v1 慢。
- **结论**：两边都没有和团队负载可比的公开数字，需要用自己的数据实测（见第 6 节）。

### 3.9 许可证

- **hftbacktest**：MIT，可以自由 fork、修改，内部闭源使用。
- **Nautilus**：LGPL-3.0，对外分发修改版需要公开修改部分的源码；商标使用受限；向上游贡献要签贡献者协议。
- **结论**：许可证层面 hftbacktest 风险更低。

| 测试与 CI  | 完整的 CI 和提交前检查（推断） | Rust 核心约 22 个单元测试，Python 只有 1 个测试文件；CI 里没有跑测试的流程；测试覆盖和 CI 都列在路线图未完成项      |

**数值精度**：hftbacktest 的价格、数量、余额、费用全部用浮点数表示，订单簿内部再按最小价格变动单位取整。
Nautilus 使用 64 位或 128 位定点数。做研究型回测问题不大；用于需要对账级精度的盈亏和费用核算时，Nautilus 更合适（推断）。

## 4. hftbacktest 逐项核实

### 4.1 做市

**具备的能力**

- **订单簿重建**：支持 L2 增量、清空、快照、最优报价，以及 L3 的新增、撤单、改单、成交事件。
- **多数据流融合**：可以把更新更快的最优挂单流和较慢的深度流合并。教程指出 Binance 最快的深度推送其实仍是聚合推送。
- **排队位置模型**：
  - **保守模型**：只有同价位发生成交才推进队列；盘口量减少时只把前方排队量截断到新的量。
  - **概率模型**：盘口量减少时，按概率把减少的量分配到自己前面或后面，并先扣除已经计入的成交量，避免重复计算。
    共 5 种概率函数，文档给出了选择函数的原则：排在队首时概率为 0，排在队尾时为 1。
  - **L3 先进先出模型**：价格优先、时间优先，回测订单插在真实订单之间，排在它后面的真实订单成交，就视为自己已经成交。
- **交易所模型**：
  - **不部分成交（默认）**：价格穿过最优价、穿过成交价，或排在队首且成交价相等时，**全部**成交；吃单不论数量都按最优价全部成交。
  - **部分成交**：排在队首且价格相等时，按剩余成交量部分成交；吃单按盘口数量成交，但盘口本身不因此改变。
  - 订单有效期支持一直有效、只做挂单、全部成交否则撤销、立即成交剩余撤销；订单类型支持限价和市价。
    在不部分成交模式下，后两种有效期的吃单也会全部成交。
- **手续费**：按成交额、按成交量、按笔三种费率模型，挂单和吃单分开，可以设负费率（返佣）；另有按买卖方向区分的费用。
- **延迟**：见 3.2 节和 4.3 节。
- **示例丰富**：GLFT 模型、网格、订单簿失衡、基差、APT、大价格单位品种的排队做市、L3 对比等。

**缺失或受限之处**

- **不模拟市场冲击**：官方建议从小单量开始，并对照实盘逐步校准。
- **自定义排队模型只能用 Rust 写**；"更多排队和交易所模型"还在路线图上。
- **L3 先进先出假设**不适用于按比例分配之类的撮合规则；收到清空消息时会清掉所有回测订单，可能和交易所实际行为不同。
- **没有资金费结算、保证金和强平**（见 3.3 节），永续合约做市的持仓成本要在策略或事后自己算。
- **数值是浮点数**（见 3.10 节）。

**结论：强。**

### 4.2 跨所套利

**具备的能力**

- **多资产多交易所**：同一个回测可以加入多个资产，每个资产单独配置数据、延迟、排队、交易所和手续费模型。
- **按交易所配置延迟**：每个资产有独立的延迟模型和行情延迟平移参数。这个平移参数的设计用途正是"行情在一处采集、策略在另一处运行"的跨所回测。
- **跨交易所同步**：统一的调度器按时间取下一个事件；前提是各交易所的本地时间来自同一个时钟（推断）。
- **相关教程**：基差做市用到现货 L1 数据；跨交易所的参数对比（Binance、Bybit、OKX、Hyperliquid 等）是按交易所分别独立回测的。

**缺失或受限之处**

- **账户和资金层面**：每个资产的余额、持仓独立，从 0 开始，权益按资产单独计算。没有共享资金、保证金、资金费、划转和提币。
- **没有跨市场示例**，Python 示例全是单资产。
- **不支持按下单、改单、撤单区分延迟**。
- **所有资产必须用同一种订单簿实现**，所以不能在同一个回测里混用 L2 和 L3 交易所（推断）。

**结论：部分。** 适合研究"跨所信号在真实延迟下能不能执行"，不适合评估资金占用、库存和保证金约束。

### 4.3 延迟评估

**具备的能力**

- **三类延迟**：行情延迟、下单发出延迟、下单回报延迟。
- **需要的数据**：
  - 行情：每条事件要有交易所时间和本地接收时间，并且接收时间必须晚于交易所时间。
  - 下单：要有请求、撮合、回报三个时间。文档建议定期提交不会成交的订单来采集。
- **采集器记录两个时间**：采集器收到消息时用本机时钟记下接收时间，按天把"纳秒时间 + 原始消息"写成压缩文件；
  交易所时间保留在原始消息里，由转换工具解析。
- **延迟扫描**：
  - 固定延迟可以直接改参数。
  - 有一个工具能用"行情延迟 × 倍数 + 偏移"合成下单延迟；教程用 4 倍和 3 倍的行情延迟演示了延迟放大对收益的影响。
  - 行情和下单延迟都可以整体平移（见 3.2 节）。
  - 文档明确把"人为降低延迟，评估升级账户等级或基础设施投入是否值得"列为用途。
- **策略可以读取当前延迟**：回测和实盘机器人都能提供最近一次的行情延迟和下单延迟。

**缺失或受限之处**

- **时钟偏差处理粗糙**：校正工具对整份文件加一个统一的偏移量，保证最小延迟不为负，处理不了随时间变化的时钟漂移；文档建议用 PTP 改善时钟同步。
- **不同数据源的时间含义不同**：Tardis 的 Binance 合约数据用的是推送时间而不是撮合时间，测出来的延迟偏小。
  交易所官方的历史数据没有本地接收时间，只能人为加延迟。
- **不模拟请求乱序到达。**
- **没有网络链路测量工具**，比如往返时间分布、丢包统计（推断这属于实盘监控的范畴）。

**结论：强。**

### 4.4 因子研究

**具备的能力**

- **Python 侧数据就是 numpy 数组**，可以直接用 polars 或 numpy 处理；依赖里包含 numba 和 polars。
- **研究示例**：
  - "定价框架"教程（标注为草稿）构造了 0.1 秒采样的"时间 × 品种"收益矩阵，计算现货收益、市场回归等信号，并在 notebook 里手写了 IC 函数。
  - "加速回测"教程通过预先计算成交条件，把单日回测从 1 分 49 秒降到 416 毫秒，适合参数搜索。
- **参数搜索**：有一个用 Python 多进程调用回测程序做网格搜索的示例。

**缺失或受限之处**

- **没有因子库接口**：Python 包里找不到 IC、相关系数、横截面分组；上面的研究代码都在 notebook 里。
- **没有数据目录或查询层**：数据按文件路径一个个加载，也没有元数据管理（推断）。
- **策略必须是 Numba 函数**（见 3.7 节），不适合大规模机器学习或 pandas 风格的研究。

**结论：弱。** 比 Nautilus 更贴近逐笔级高频信号研究的写法，但仍需要独立的研究工具。

### 4.5 行情数据评估

**具备的能力**

- **采集器**：支持 Binance 现货、Binance U 本位和币本位合约、Bybit、Hyperliquid。
  - Binance 合约数据流会比对相邻两条消息的序列号来检测断档，断档时限速重新拉取快照。
  - Bybit 和 Hyperliquid 的采集代码里没有找到断档或序列号检测。
- **校正与校验工具**：
  - 时间戳校正：修正负延迟。
  - 事件顺序校正：交易所时间和本地时间的先后顺序不一致时，把事件拆成交易所侧和本地侧两份，分别排序。
  - 顺序校验：检查两侧时间是否单调递增。
- **订单簿工具**：可以生成日终快照供第二天使用，也可以从快照流生成增量。
- **交易所数据对比示例**："融合深度数据"教程比较了 L2 深度流和最优挂单流的更新频率和领先关系。

**缺失或受限之处**

- **转换工具不检查序列号**：Binance 转换工具读取深度更新时不使用序列号字段，断档只能靠采集端补快照。
- **没有数据质量报告**：缺口统计、交易所间一致性、数据商对比都没有。
- **转换工具按文件整体载入内存**，并预先分配一个很大的缓冲区（默认 1 亿条，每条 64 字节），大文件需要手动调参。

**结论：部分。**

### 4.6 数据接入

- **格式**：8 个字段，包括事件类型、交易所时间、本地接收时间、价格、数量、订单编号和两个附加字段；
  事件类型里同时编码了买卖方向和"交易所侧 / 本地侧"标记。文件可以从 S3 读取，Python 包默认已开启这项功能。
- **现成的转换工具**：
  - Binance 合约原始数据流，可选包含标记价格和最优挂单作为自定义事件。
  - Binance 和 Bybit 的官方历史数据（没有本地接收时间）。
  - Bybit 原始数据流，含多深度融合。
  - Hyperliquid 原始数据流、MEXC 现货、Tardis。
  - Databento，只支持逐笔订单，需要额外安装 Databento 的包。
  - 旧版本数据的迁移。
- **Databento 适配度**：转换时同时保留交易所时间和接收时间，L3 教程用的就是 CME 逐笔订单数据。
  对团队来说，CME 加密期货的逐笔订单数据可以用 L3 先进先出模型精确回测，这是 hftbacktest 的一个亮点（推断）。
  局限是转换时整体载入、逐行用 Python 循环处理，大文件会比较慢（推断）。
- **Pyth**：没有任何支持。可行的接入方式（推断）：
  - Pyth 的发布时间和本地接收时间正好对应交易所时间和本地时间，可以做成一个按本地时间查找的数组，
    在策略里按当前时间查最近的值，教程演示过这种做法。
  - 也可以编码成自定义事件混进事件流（Binance 转换工具有先例），但 Python 侧没有读取自定义事件的接口，需要用 Rust 包装。
- **团队自有交易所数据要做的事**：
  1. 每条消息都必须有本地接收时间。如果历史数据只有交易所时间，延迟研究就会失真。
  2. 按交易所把数据解析成上述 8 字段格式，区分快照（先清空，再写快照）和增量。
  3. 成交和由成交引起的深度变化，先后顺序会影响排队估计。Tardis 转换工具要求成交文件先于深度文件输入，以免重复扣减。
  4. 依次运行时间戳校正、事件顺序校正和顺序校验，按天输出数据文件，并生成日终快照。

### 4.7 实盘

- **架构**：连接器是一个独立进程，通过共享内存服务多个机器人，只能在同一台机器上运行；通过网络远程通信还在路线图上。
- **交易所**：Binance 合约（测试网验证）、Bybit（开发中），代码里另有 Binance 现货。
  OKX、Hyperliquid、Coinbase、Kraken 和 Databento 实时行情都在路线图的未完成项里。
- **同一份策略代码**：Rust 侧回测器和实盘机器人实现同一个接口，示例里同一个网格策略函数既用于回测也用于实盘。
- **风险声明**：连接器写明"风险自负，并非所有情况都能正常工作"；Binance 下单走 REST，WebSocket 下单还在路线图上。
- **成熟度判断（推断）**：适合个人或小团队在单一交易所做原型验证；对管理 5 亿美元规模资金的团队来说，缺少对账、风控和多交易所覆盖，不适合作为生产实盘。

### 4.8 工程与风险

- **许可证**：MIT（见 3.9 节）。
- **版本与稳定性**：见 3.10 节。Python 包标为"生产可用"，Rust README 却写着"初始开发阶段"，两者互相矛盾。
- **发布节奏**：浅克隆只有一个提交，从仓库判断不了发布节奏；仓库里有 Python 包的发布流程。
- **单人维护风险**：包的作者元数据只有一人（见 3.10 节）。但代码量不大，又是 MIT 许可证，团队有能力自己维护一个 fork（推断）。
- **文档质量**：数据、延迟、成交几篇概念文档短而准确，和源码一致；大量知识散落在 notebook 里；Rust API 文档依赖自动生成的站点。
- **组合、会计、报表**：只有按资产的记录和 17 个指标（见 3.6 节），没有组合盈亏归因、逐笔成交日志或 HTML 报告。
- **界面**：没有。

## 5. 平台层自建工作量对比

| 模块                 | 以 Nautilus 为基础                                 | 以 hftbacktest 为基础                               | 组合方案的额外成本                                                        |
| -------------------- | -------------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------- |
| 原始数据层           | 加载工具写入数据目录；需要补 Pyth 的自定义数据     | 每个交易所写一个转换工具，按天切分并生成日终快照    | 统一原始层，同时保留交易所时间和本地接收时间，分别导出两种格式            |
| 数据目录与查询       | 已有 Parquet 数据目录和 SQL 查询                   | 没有，需要自建文件索引和元数据                      | 以 Nautilus 数据目录或独立的数据湖为准                                    |
| 数据质量             | 自建缺口、序列号、跨所一致性检查                   | 复用采集器的断档补快照和顺序校验，仍需自建质量报告  | 一套质量检查即可，放在原始数据层                                          |
| 行情与延迟采集       | 自建本地接收时间埋点和延迟数据库                   | 可直接用采集器（仅 5 类交易所），需自建下单延迟采集 | 采集器的产出同时服务两个引擎                                              |
| 延迟模型             | 要扩展到行情延迟和回报延迟，需要改撮合核心（推断） | 已具备；自定义模型要写 Rust                         | 延迟研究集中在 hftbacktest                                                |
| 账户、保证金、资金费 | 已有；划转和提币需要用自定义仿真模块自建           | 全部自建，包括跨资产的资金池                        | 放在 Nautilus                                                             |
| 组合与报表           | 有统计量和 HTML 报告，需要把年化改成 365 天        | 只有按资产的指标，组合汇总要自建                    | 统一结果模型，两个引擎都导出到同一个结果库                                |
| 任务调度与参数扫描   | 多进程或容器调度，重置后可复用已加载数据           | 多进程调度，可以借鉴"加速回测"的做法                | 一个调度器，两类任务模板                                                  |
| 网页后台             | 全部自建                                           | 全部自建                                            | 一个界面，两类引擎后端                                                    |
| 实盘                 | 已有多交易所接入和对账                             | 需要补齐交易所、对账、风控，或另选实盘系统          | 实盘统一走 Nautilus；hftbacktest 的研究结论要在 Nautilus 里重写策略       |
| 策略代码复用         | 回测和实盘共用一套代码                             | Rust 侧回测和实盘共用；Python 只能回测              | 两套策略代码，需要建立"hftbacktest 研究、Nautilus 实现"的交接和一致性测试 |

**工作量判断（推断）**：

- 只用 Nautilus：缺口集中在"行情延迟和回报延迟"的建模，这要改撮合核心，风险最高。
- 只用 hftbacktest：缺口集中在账户、组合和实盘，工作量最大。
- 组合方案：两个核心引擎都不用改，新增工作集中在统一数据层、结果库和界面，以及策略从 hftbacktest 迁到 Nautilus 的流程。
  三种方案里这个风险最可控。

## 6. 待解决问题

需要用团队自己的数据动手验证的事项：

1. **排队模型校准**：在团队主要的做市品种上，用实盘成交记录对比 hftbacktest 的保守模型、各个概率模型和 Nautilus 排队跟踪的成交率，确定哪种最接近实盘。
2. **自有数据的本地时间戳质量**：现有交易所历史数据有没有采集端接收时间、时钟用什么方式同步（NTP 还是 PTP）、有没有随时间变化的漂移。
   这决定 hftbacktest 的行情延迟模拟是否可信（见 4.3 节）。
3. **吞吐量和内存**：按典型规模（比如 10 到 50 个品种、多个交易所、一个月全量 L2）分别实测两个引擎的运行时间和峰值内存。
   两边都没有可比的公开数字（见 3.8 节）。hftbacktest 要重点测数据整体载入和多资产调度的开销。
4. **一个回测里放多个交易所**：在 hftbacktest 里把同一品种的两个交易所放进同一个回测，验证跨所下单的时序和延迟平移是否符合预期，因为官方没有这类示例（见 4.2 节）。
5. **Databento 逐笔订单转换的规模**：在 CME 加密期货一整天的逐笔订单文件上，测转换的耗时和内存（见 4.6 节）。
6. **Pyth 数据形态**：确定用 Hermes 历史价格还是链上更新，以及有没有团队自己的接收时间，再决定两边的接入方式。
7. **Nautilus 回测中交易所回报有没有延迟**：Nautilus 评估遗留的问题，直接影响"在 Nautilus 里复现 hftbacktest 做市结论"的可行性。
8. **hftbacktest 上游的活跃度**：本地是 fork 的浅克隆，判断不了原作者仓库现在的发布节奏和问题响应速度，需要到 GitHub 上核实。
9. **研究到实盘的一致性**：选一个做市策略，分别在 hftbacktest 和 Nautilus 里实现，用同一份数据回测，量化两边结果的差异，作为组合方案交接流程的基准。
