# NautilusTrader 作为加密团队回测基础设施的适配性评估（v2）

本版是第一版评估的纯文档版本，去掉了代码标识、文件路径和行号引用，只保留结论和理由，便于非技术读者阅读。
评估对象是 NautilusTrader v2 的第八个候选发布版（2.0.0rc8）。所有结论都来自对其官方文档和源码的核实；
需要逐条查证出处时，请看同目录下的第一版。标"（推断）"的结论不是文档或源码的直接陈述，而是根据它们推理得出的。

## 1. 结论摘要

**总体判断**：NautilusTrader 适合作为"对执行细节敏感的策略"的回测引擎内核，比如做市，以及跨所套利的下单执行部分。
但它刻意不提供平台层能力：网页界面、分布式任务调度、超参数优化、数据质量平台都不在项目范围内，需要团队自建。
对因子研究和行情数据评估这两类工作，它只能充当数据访问层或策略验证环节，替代不了向量化研究工具和数据平台（推断）。

**最重要的五项发现**：

1. **撮合模拟很细，但延迟只模拟了"下单指令发往交易所"这一个方向。**
   延迟模型只作用于下单、改单、撤单三类指令。行情传到策略的延迟、交易所回报（受理确认、成交通知）传回策略的延迟，
   都没有建模。官方文档对沙盒模式明确写了"只覆盖入站一腿"。
2. **历史订单簿不会被模拟成交改变，所以自己订单的市场冲击没有建模。**
   "成交后消耗盘口流动性"这个选项默认关闭；关闭时，同一档挂单量可以被多张模拟订单重复成交。
   "用户订单与盘口的交互、盘口的持久性变化"仍在官方路线图的待办事项里。
3. **跨交易所的资金划转、提币和链上结算完全没有建模。**
   每个交易所各自有独立的起始余额和账户，回测引擎里没有任何划转、提币或充值逻辑。
   只能通过底层接口手动调整账户余额，或用自定义的仿真模块来近似。
4. **数据接入方面**：Databento 和 Tardis 有官方加载工具，CoinAPI 也有（测试版）。**Pyth 没有任何接入。**
   Pyth 数据只能作为"自定义数据"导入；而高层回测接口不接受自定义数据，所以只能用低层回测引擎来跑。
5. **发布状态与扩展方式**：v2 仍是候选发布版，标为 Beta，每个候选版都带大量不兼容改动，第八版就有 62 条。
   并行回测只能靠多进程：同一进程里不能同时跑多个回测，一个高层回测任务也只接受一套运行配置。

**各场景结论**：做市为较强；跨所套利为较强，但仅限下单执行部分；延迟评估为部分；因子研究为弱；行情数据评估为弱。

## 2. 场景逐项评估

### 2.1 做市

**具备的能力**

- **L2/L3 订单簿回放**：模拟交易所可以按最优报价（L1）、按价位聚合的深度（L2）或逐笔订单（L3）来维护订单簿，
  订单簿增量数据会在 L2/L3 模式下驱动盘口变化。高层回测接口默认把一批增量合成一个完整事件后再撮合。
- **排队位置跟踪**：需要同时开启"排队位置"和"按逐笔成交撮合"两个选项。挂单被受理时，系统记下同价位前面排着多少量，
  之后随着对手方向的成交逐步扣减。L3 数据下按逐笔订单精确推进队列；L1 数据下有基于报价的近似规则。
- **流动性消耗**：开启后会按价位记录已被模拟成交消耗的量，下一次盘口更新到来时重置。
- **成交模型**：内置 11 种，也支持自定义模型，自定义模型可以返回一个合成的订单簿。
- **手续费、保证金与资金费**：手续费模型必须显式配置；资金费率数据会在结算时点结算到持仓上；支持强平。
- **自有订单簿**：可以单独跟踪自己的挂单，并从公开盘口中扣除。
- **示例**：官方有网格做市和订单簿回测的教程。

**缺失或受限之处**

- **不模拟市场冲击和其他参与者的反应**：历史订单簿不可变，相关能力仍在路线图上。
- **排队跟踪有局限**：只支持限价单；每张单独立估计；看不到隐藏单。
  交易所数据里不标买卖方向的成交会同时扣减两侧队列，结果偏乐观。
- **延迟只覆盖下单方向**，详见 2.3 节。
- **大量成交累积到同一持仓时，v2 反而比 v1 慢**：官方基准里，4,000 笔成交累积到一个持仓的场景，v2 比 v1 慢 63.9%，
  其中约 64% 的 CPU 时间花在复制持仓对象上。做市策略成交笔数通常很多，这一点直接相关（推断）。
- **加密交易所很少提供 L3 数据**：Tardis 的盘口变化数据只能还原为 L2 增量，多数交易所只能做 L2 级别的排队估计（推断）。

**结论：较强。**

| 初步判断             | 核实结果 | 说明                                                       |
| -------------------- | -------- | ---------------------------------------------------------- |
| L2/L3 增量回放       | 已证实   | 三种订单簿模式均支持                                       |
| 排队位置跟踪         | 已证实   | 但只支持限价单，且依赖逐笔成交数据                         |
| 延迟模型             | 需修正   | 只延迟下单指令，不覆盖行情延迟和回报延迟                   |
| 可配置成交模型       | 已证实   | 11 种内置加自定义                                          |
| 保真度取决于数据粒度 | 已证实   | 官方文档明确说明                                           |
| 适配度为"强"         | 需修正   | 下调为较强：不模拟自身冲击、延迟单向、成交量大时性能会退化 |

### 2.2 跨所套利

**具备的能力**

- **一个回测里同时跑多个交易所**：一次回测可以同时包含多个交易所和多个策略。
- **按交易所分别配置**：延迟、成交和手续费模型都可以按交易所单独设置，所以每个交易所可以有不同的延迟。
- **资金费**：有资金费率数据类型和结算机制；高层回测接口能加载资金费率、标记价格和指数价格。
- **组合视图**：可以按交易所和账户查看敞口和权益。
- **同一时刻的连锁下单**：比如一条腿成交后立刻下对冲单，这些指令可以在同一个时间点内处理完。

**缺失或受限之处**

- **跨所划转、提币、充值、链上确认和结算周期都没有建模**：每个交易所的起始余额相互独立。
  手动调整账户余额的接口只在底层可用，Python 接口里没有。用自定义仿真模块生成余额调整来近似划转是可行的（推断）；
  但每个模块只能看到单个交易所的只读快照，一笔划转的两端要靠两个模块配合实现（推断）。
- **资金费数据入库有缺口**：
  - 用 Tardis 回放服务写入数据目录时，不会写入资金费、标记价格和指数价格。
  - Python 的数据目录接口没有写入资金费的方法，流式写入也不接受它。
  - 可行的办法有三种：用 Tardis 的 CSV 加载工具读取资金费率；在低层回测引擎里直接添加数据；用 Rust 写入数据目录。
- **没有现成的套利示例或教程。**

**结论：较强**（仅限下单执行、价差和资金费收益；涉及资金和库存约束时为"部分"）。

| 初步判断               | 核实结果 | 说明                               |
| ---------------------- | -------- | ---------------------------------- |
| 一个回测多个交易所     | 已证实   | 官方明确支持                       |
| 按交易所配置延迟       | 已证实   | 但同样只覆盖下单方向               |
| 资金费数据类型         | 已证实   | 但 Python 侧缺少写入数据目录的方法 |
| 划转、提币、结算"未知" | 已否定   | 已确认完全没有建模                 |

### 2.3 延迟评估

**具备的能力**

- **回测侧**：
  - 可以写自定义延迟模型，按每条指令返回一个延迟值；也可以按订单编号查表，回放实测的延迟。
  - 指令到达交易所的时间等于指令创建时间加上延迟，延迟中的指令按顺序释放。
  - 因此可以做延迟参数扫描，回答"慢多少毫秒会损失多少"。
- **实盘侧的时间戳**：
  - 所有行情数据和事件都带两个时间戳：事件发生时间，以及本地创建这条数据的时间（对外部数据来说通常就是接收时间）。
  - 订单报告和成交报告也带相应的时间戳。
  - 官方文档明确提醒：两个时间戳相减，只有在两边时钟同步时才代表真实延迟。
- **实盘运行指标**：Rust 版实盘节点能提供消息分发速率、队列深度、利用率等进程内指标，但不包含网络往返时间。
- **沙盒模式**：真实行情加模拟撮合，也可以挂延迟模型。
- **数据源时间戳**：Tardis 数据的事件时间是交易所时间，接收时间是采集端的本地时间，
  所以可以估计"交易所到采集端"的延迟，但会受时钟偏差影响。

**缺失或受限之处**

- **回测不模拟行情延迟和回报延迟**：
  - 数据按接收时间排序回放，策略在同一时刻就收到数据。
  - 交易所生成的回报不延迟：沙盒模式有明文说明；回测的延迟模型只有三类下单指令，据此推断回测中同样如此（推断）。
- **Databento 丢失了撮合引擎时间**：Databento 的报价和成交数据把它的接收时间当作事件时间，
  原始撮合引擎时间没有进入核心数据（推断）。这对延迟研究影响较大。
- **没有面向网络链路的延迟测量或指标导出工具**：没有 Prometheus 或 OpenTelemetry 这类导出；
  上面提到的进程内指标在 Python 侧也没有开放。

**结论：部分。**

| 初步判断                     | 核实结果 | 说明                                           |
| ---------------------------- | -------- | ---------------------------------------------- |
| 可扫描模拟延迟               | 已证实   | 支持自定义延迟和实测延迟回放                   |
| 真实链路延迟属于实盘测量问题 | 已证实   | 没有专门的测量工具                             |
| 数据带两个时间戳             | 已证实   | 事件时间和本地接收时间                         |
| 延迟和指标工具               | 需修正   | 只有进程内运行指标，没有网络往返或延迟分布工具 |

### 2.4 因子研究

**具备的能力**

- **流式技术指标**：约 41 个指标，覆盖均线、动量、比率、支撑阻力、波动率和订单簿类指标，逐条数据更新。
- **从数据目录查询到表格**：可以直接把数据查成 PyArrow、pandas 或 Polars 表格，支持 SQL 过滤条件和时间范围；
  数据目录可以放在 S3、GCS 或 Azure 上。
- **自定义数据**：因子信号可以注册为自定义数据，写入数据目录，并推送给策略。
- **绩效统计**：内置 34 个统计量。

**缺失或受限之处**

- **引擎是事件驱动的**：没有向量化或横截面计算接口，也没有 IC、分组回测这类因子评估功能。
  官方甚至把"向量化研究"列为它要替代的另一种做法。
- **高层回测接口不能直接加载自定义数据（也就是因子）**：只能用低层回测引擎添加。
- **自定义统计量也只能在低层回测引擎上注册。**
- **夏普比率默认按 252 个交易日年化**：加密市场全年无休，需要自行调整（推断）。
- **超参数优化和 AI/ML 工具明确不在项目范围内。**

**结论：弱**（作为因子研究引擎）。适合放在"因子变成策略"后的事件驱动验证环节（推断）。

| 初步判断             | 核实结果 | 说明                                         |
| -------------------- | -------- | -------------------------------------------- |
| 事件驱动、非向量化   | 已证实   | 官方定位如此                                 |
| 有技术指标           | 已证实   | 约 41 个                                     |
| 支持自定义数据       | 已证实   | 但高层回测接口不支持                         |
| 数据查询能力         | 需修正   | 比预想强：可以直接输出 pandas 或 Polars 表格 |
| 批量或向量化分析接口 | 已证实   | 确实没有                                     |

### 2.5 行情数据评估（数据质量与交易所数据评估）

**具备的能力（多为零散的校验功能，不是成套工具）**

- **数据覆盖区间**：可以查询数据目录里某类数据覆盖了哪些时间段、缺了哪些时间段，以及最早和最晚的时间。
- **写入保护**：默认拒绝时间重叠的写入，并提供文件修复与合并操作。
- **订单簿完整性检查**：可以检查盘口是否出现买卖价交叉、层级是否合规，但需要主动调用。
  乱序的增量数据会被照常应用，只记录一条警告，不会被拒绝。
- **回放时的校验**：
  - 数据精度与品种定义不符时，告警并跳过，连续 20 次后报错。
  - 订单簿增量数据缺少"批次结束"标记时，回测直接失败。
  - Tardis 加载工具会跳过第一个完整快照之前的数据。
- **微观结构指标**：价差分析、订单簿买卖失衡比。
- **订单簿分析**：可以计算吃掉指定数量的平均成交价，或模拟一笔订单会如何成交。

**缺失或受限之处**

- **没有数据质量报告或定期检查任务**：覆盖区间是根据文件名里的时间范围判断的，
  文件内部的缺口检测、序列号断档统计、跨交易所一致性对比都需要自建（推断）。
- **时区处理有已知问题**：查询引擎使用的时区库与核心库版本不一致。

**结论：弱。**

| 初步判断                   | 核实结果 | 说明                                                         |
| -------------------------- | -------- | ------------------------------------------------------------ |
| 属于数据平台工作，适配度弱 | 已证实   | 只有零散的校验功能，没有数据质量工具                         |
| 用 Parquet 格式的数据目录  | 已证实   | 官方标准存储方式                                             |
| 有数据校验或完整性检查     | 需修正   | 有若干校验功能（盘口完整性、重叠写入、覆盖区间），但不成体系 |

## 3. 场景 × 问题 × 数据粒度 × 保真度矩阵

| 场景         | 回测能回答的问题                       | 所需数据粒度                                   | 保真度                                        | 回测无法回答的问题                                 |
| ------------ | -------------------------------------- | ---------------------------------------------- | --------------------------------------------- | -------------------------------------------------- |
| 做市         | 报价策略的成交率、库存、价差收益和费用 | L2 增量加逐笔成交，最好有 L3 逐笔订单          | L3 加成交时高；L2 是排队估计；L1 依赖概率模型 | 自身挂单对他人行为的影响、隐藏单、真实的优先级规则 |
| 跨所套利     | 价差捕获、对冲腿滑点、资金费收益       | 各交易所的 L1/L2 加成交加资金费，时间轴统一    | 下单执行部分中高；资金层面低                  | 划转和提币的耗时与费用、交易所风控、各所时钟偏差   |
| 延迟评估     | 策略收益对下单延迟有多敏感             | 带事件时间和接收时间的逐笔数据，加实测延迟分布 | 只覆盖下单方向                                | 行情延迟、回报延迟、真实链路的抖动与丢包           |
| 因子研究     | 因子变成策略后的事件驱动表现           | K 线或逐笔数据，因子作为自定义数据提供         | 执行层高；因子统计层面不支持                  | IC、衰减、横截面分组、大规模参数搜索               |
| 行情数据评估 | 数据能否回放、盘口是否完整、覆盖区间   | 原始逐笔或订单簿数据                           | 只有零散的校验功能                            | 交易所间数据一致性、序列断档统计、数据商对比       |

补充说明：

- 数据粒度必须和订单簿模式一致。NautilusTrader 不能从低粒度数据生成 L2/L3 订单簿。
- 用 K 线数据时，无法知道 K 线内部的价格先后顺序、价差、深度和排队位置。
- 交易所打印出来的成交，只能证明那一刻存在流动性，不代表你的订单也能成交。
- 成交模型和延迟模型都不能决定实盘的成交结果。

## 4. 数据接入

### 4.1 通用转换路径（自有交易所数据）

- **官方流程**：用加载工具读入源数据 → 统一字段、时间戳和精度 → 构造成标准数据对象 → 写入数据目录，或直接加入回测。
- **先写品种定义，再写行情**。每次写入只能包含一个品种，并且要按接收时间升序排列。
- **现成工具**：
  - 通用的 CSV/Parquet 加载工具，输出 pandas 表格。
  - Arrow 格式转换工具，但要求输入已经符合 NautilusTrader 的数据结构。
  - Binance 深度数据的 CSV 加载工具。
  - 官方有一个端到端示例：外部 CSV 写入数据目录，再用高层回测接口运行。
- **精度要求**：价格和数量必须与品种定义的精度一致，否则会被跳过或拒绝。官方安装包默认使用 128 位、16 位小数的高精度模式。
- **CoinAPI（测试版）**：支持从 S3 上的 CSV 文件加载。
- **交易所接入以实盘为主**：把实盘数据回写到数据目录的功能，只适用于 Databento 这类明确支持的接入。

### 4.2 Databento

- **加载**：可以把 Databento 的原生文件解码成标准数据，覆盖逐笔订单、最优报价、十档深度、成交、K 线、品种定义、交易状态等。
- **建议一次性写入数据目录**：之后从 Parquet 读取，比每次重新解码原生文件快至少一个数量级。
- **与加密业务的关系**：Databento 是传统资产数据商。和加密业务相关的，主要是 CME 期货数据，以及作为信号源的传统资产（推断）。
- **时间戳映射**：报价和成交数据把 Databento 的接收时间当作事件时间，这对延迟研究有影响。

### 4.3 Tardis

- **CSV 加载与流式读取**：支持订单簿增量、五档和二十五档快照、报价、成交、资金费率和期权链。
- **Tardis 回放服务写入数据目录**：支持，但不写入资金费、标记价格和指数价格。
- **不支持的格式**：最优挂单推送和强平数据。
- **其他限制**：实时接入不支持历史数据请求；不建议使用混合了多个品种的 CSV 文件。

### 4.4 Pyth

- **核实结果：没有任何 Pyth 接入（已证实）。** 在代码、文档和示例中都找不到，官方接入清单里也没有。
  唯一相关的是 Polymarket 数据里有一个字段的取值可以是"pyth"。
- **可行路径（推断）**：
  - 把 Pyth 的价格、置信区间、发布时间等字段定义为自定义数据类型，写入数据目录时要满足数据结构和按时间升序的要求。
  - 回测时通过低层回测引擎加入数据。自定义数据只会推送给策略，不参与撮合。
  - 如果只需要价格，也可以转成标准的"指数价格"类型，但这样会丢掉置信区间等 Pyth 特有的信息。
- **新的官方接入需要先走提案（RFC）流程。**

## 5. 风险与限制

### 5.1 发布状态

- v2 是候选发布版（2.0.0rc8），标为 Beta，安装时需要显式允许预发布版本。
- 候选版节奏：第三版发布于 2026-08-20，第七版发布于 2026-10-15，第八版尚未发布。
- 不兼容改动多：第七版有 43 条，第八版有 62 条，其中包括延迟模型接口、模拟交易所配置等回测相关的接口。
- v1 已转入维护分支，切换后大约三个月内只接收关键安全补丁。最后一个 v1 版本发布于 2026-08-02，
  据此推算 v1 维护期大约在 2026 年 11 月前后结束（推断）。

### 5.2 许可证

- 采用 LGPL-3.0。
- 内部使用且不对外分发时，通常不触发公开源码的义务；如果对外分发修改过的库，需要按 LGPL 提供修改后的源码。
  这里的理解需要法务确认（推断）。
- 项目名称和商标的使用受限，向上游贡献代码需要签署贡献者协议（CLA）。

### 5.3 界面与平台

- 可视化输出是自包含的交互式 HTML 报告，不需要后端服务。
- 网页界面和仪表盘明确不在项目范围内；路线图里的可视化工作也限定为"不做完整的界面仪表盘"。
- 分布式任务调度和超参数优化同样不在范围内。
- 这些话题也不允许在官方渠道讨论。

### 5.4 性能

- **官方基准**：2 万个事件的纯回放约 23 毫秒，测试负载是单交易所、1 分钟 K 线加报价。
- **v2 与 v1 对比**：32 组对比中 v2 有 30 组更快，比如十档深度场景快 90.6%；但"大量成交累积到同一持仓"的大规模场景 v2 更慢。
- **没有测量的方面**：峰值内存、大规模数据目录或流式负载、多交易所场景。
  因此对于做市和跨所套利的真实负载，没有现成的吞吐量数据。
- **Python 回调是同步执行的**，必须尽快返回，否则会拖慢整个回测。

### 5.5 并行与可复现性

- **并行**：同一进程内不能同时运行多个回测节点，一个高层回测任务也只接受一套配置，所以并行只能靠多进程。
- **复用已加载的数据**：重置后可以复用已加载的数据做参数扫描，不必重新加载。
- **确定性**：
  - 回放按接收时间稳定排序，成交编号是确定性生成的。
  - 成交模型如果不设随机种子，会使用操作系统的随机源，结果不可复现。
  - 自定义 Python 模型的内部状态会在重置后保留，需要自己处理。
  - 官方基准测试中，预加载和重新加载两种方式的结果摘要一致。
  - 确定性仿真测试（DST）主要面向实盘运行时，对回测只约束交易所和品种的迭代顺序。

### 5.6 已知限制

- 高层回测接口不支持自定义数据、直接传入表格和下载数据。
- 不能为高层回测接口注册自定义统计量。
- 同一个数据目录实例上，不能一边查询一边写入。
- v1 的数据目录需要迁移后才能使用。

## 6. 平台层需要自建的部分

| 模块           | 需要自建的内容                       | NautilusTrader 可以依托的能力                                            |
